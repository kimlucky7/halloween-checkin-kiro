# Design — Halloween Check-in

状态：建议设计，非已有接口保证。以下操作名、记录类型和字段为新项目的逻辑契约，不表示现有 August API 支持它们。Kiro 实施时先确认 SDK、运行时与传输限制，再定具体路由和 schema。

## 1. 组件与责任

1. **代理入口 / Skill**：识别 checkin 与主题，读取已授权照片，调用可用图像能力，组织审核与确认；不持有部署管理员凭据
2. **Image Provider Adapter**：区分宿主代理生成和 API 服务生成。统一输入意图、源图引用、主题、阶段与能力声明；统一返回图片引用、提供者、模型标识（可得时）、尝试次数与错误。仅声明已验证能力，不虚构 Kiro/ChatGPT API
3. **本地准备与校验器**：真实解码、归一化、透明处理、共享构图、预览与质量报告；第一版作为独立可测试模块，不在 Worker 中任意解码大图片
4. **审核与发布服务（独立 Worker）**：认证、草稿版本、审核包、批准绑定、幂等写入和状态查询。Worker 再做输入与容器完整性验证；不因客户端报告 PASS 就接受任意文件
5. **D1**：草稿、版本、发布操作、元数据与不可变媒体 manifest 的唯一可见性来源
6. **R2**：私密临时区域与最终媒体。原图默认留在代理受控临时环境，不传发布服务；最终对象不可覆盖。不可通过猜测对象键绕过公开记录检查
7. **展示前端**：可选 Astro 或实现时确认的轻量方案；读已发布投影、主题/昼夜选择、可选节日氛围

### Provider 选择

- MVP 先支持 `host-generated`：ChatGPT 等有图像能力的宿主产出图片，校验器接收实际文件；其发布 MCP 不负责生成
- `api-generated` 可作为后续适配器，须确认服务、权限、费用、图片编辑/透明能力、超时和数据处理条款，再接入
- 两种适配器输出同一个审核契约。没有已配置生成能力时显示“待导入图片/模拟流程”，不能悄悄发送到另一个服务

## 2. 核心数据（逻辑模型）

- **CheckinDraft**：不可猜测 draftId、从认证主体得到的 ownerId、环境/项目 ID、状态、创建时间、当前 revision
- **DraftRevision（不可变）**：revisionId、theme、公开 text、可空 place/companions/capturedAt、timestamp 来源与时区、pair manifest、公开差异说明、校验器版本与报告摘要、payloadHash
- **PairManifest**：该主题的 day/night 对象或待上传文件引用、各自 SHA-256、MIME、字节数、720×720/alpha 检查结果、共享变换参数和私密预览引用
- **Approval**：approvalId、revisionId、payloadHash、目标项目/可见性、认证主体、确认时间、确认来源/信任级别、有效期和撤销状态。不得保存整段私密聊天作为公开证明
- **PublishOperation**：随机 operationId/idempotencyKey、ownerId、revisionId、payloadHash、状态、结果 checkinId、可恢复错误类别
- **PublishedCheckin**：稳定 checkinId、publishedAt、可空 capturedAt、公开元数据、当前版本引用和主题 manifest 引用。普通与 Halloween 可归属同一条打卡的独立变体；关联必须由已知 ID/用户确认，不按相似地点名字自动合并

第一版可以只有一种主题，不强制普通+节日四张图同时存在。每个已存在主题必须有完整 day/night 一对。生成历史、原照片、内部对象键和审批记录不进入公开投影。

## 3. 状态机与批准边界

草稿版本依次经历：`created → generating → preparing → review_ready → approved → publishing → published`。失败记在对应阶段，取消进入 `cancelled`；修改建立新 revision 并回到适当阶段，不原地改写获批版本。

批准只针对 `review_ready` 的不可变版本。确认对象是用户刚看到的最终图与公开数据；生成草稿阶段的“好/继续”不跳过审核。过期策略由服务统一配置，默认采用短期审核会话，不写死为活动规则。批准过期或撤销后不得启动新发布；已提交的发布须报告实际状态，不能保证撤销能抢先终止已提交事务。当前调用者通过身份、所有权及项目校验，且操作键与原 revision/hash 完全匹配时，可以查询或幂等重放已有结果；这不授予新的写入权限。未完成操作在此路径只返回实际状态，不创建新操作或新媒体/记录，不重新触发发布。需要新副作用的恢复须重新审核并取得有效批准。

**可信代理模式的限制**：代理在对话中判断用户的明确发布意图，提交绑定该版本的批准声明。服务端可验证认证身份、哈希、目标与版本，但仅凭同一代理的声明无法独立证明真人点击；日志应标记为 `trusted-agent-attestation`，不得夸大。若要更强保证，增加独立的已认证网页审核按钮来签发一次性批准票据。二者不得混为同一证明级别。

payloadHash 对规范化的公开内容、图片字节哈希、主题、版本、目标项目和可见性计算。先冻结字段规范（Unicode/空值/排序/时间格式），再哈希；服务端重算。不要对带过期签名的 URL 或随机 JSON 序列化直接计算哈希。校验报告引用也与版本绑定，图片变化时必须重跑。

## 4. 端到端时序

1. 入口确认源图可读、数据授权与主题；在私密临时目录建立工作区
2. 白天生成与身份检查；以接受的白天图制作同主题夜景。保留尝试次数和错误，不记录密钥
3. 准备器将两张图共同归一化为交付版本，生成多尺寸预览；执行自动校验和视觉审核
4. 创建不可变审核 revision。文件跨环境时必须实际传输并验证哈希，不把另一个执行器的路径当可读文件
5. 展示审核包后停止。用户修改则新建 revision；明确发布才记录对应批准
6. 发布服务验证身份、输入、批准与哈希，建立或复用 PublishOperation
7. 存储完整最终一对，验证各对象；最后一次 D1 原子提交引用与 published 状态
8. 返回稳定记录/操作 ID。客户端查询记录并校验公开图片可读和正确 MIME；结果不明先查操作状态
9. 清理私密临时文件；前端只能展示 D1 已提交的公开记录

## 5. 逻辑 API / MCP 契约

实现时定义版本化 schema；下列仅为能力清单：

- 准备/注册审核包：输入元数据、成品和校验描述，返回 revisionId、服务端 hash 与审核结果；不得顺带公开
- 批准当前版本：记录批准来源和版本；不是绕过用户确认的自动步骤
- 发布已批准版本：输入 revisionId、hash、批准引用与幂等键，输出操作状态及成功时的记录 ID
- 查询发布操作 / 读取本人草稿：用于恢复，只允许该 owner
- 读取公开列表 / 公开媒体：仅已提交的安全投影

是否直接传文件、分阶段上传或安全临时引用，须依据真实 MCP 宿主的文件协议确定。不得假设 ChatGPT 本地绝对路径可被远端 Worker 读取，也不接受任意第三方 URL 导致 SSRF。若支持上传会话，绑定 owner、revision、大小、MIME、hash、有效期和次数；本地路径只由宿主负责传输。

发布返回结构应区分：已发布、处理中、需重新审核、输入不合格、认证失败、哈希/幂等冲突、可恢复存储错误。任何不明确网络结果都不能被描述成“肯定没发布”。

## 6. 并发、一致性、重试

- D1 对 owner+idempotencyKey 建唯一约束，对同一已批准 revision 的最终发布建唯一约束。并发请求先原子争用同一操作；禁止“先查没有再插入”的竞态
- 先验证当前调用者身份、所有权和项目，再按原操作键及 revision/hash 查找已提交操作。相同键与相同 hash 返回同一状态/已有结果，即使批准随后过期或撤销；相同键不同 hash 返回冲突。此重放只读已有结果，不产生新的副作用，也不绕过身份校验。只有不存在已提交操作并且批准仍有效、未撤销时，才可原子争用新发布；需要新副作用的恢复须重新审核并取得有效批准
- R2/D1 无跨服务事务：使用不可变版本化对象键，先完整写媒体，后原子提交可见记录。提交失败时对象仍不可公开引用，操作可恢复或安全清理
- 公共媒体路由检查对象是否被已发布 manifest 引用，避免未批准内容因提前上传而公开；缓存只对已发布不可变资源生效
- 异步清理仅处理明确过期、无引用、无进行中操作的临时对象，不清理原项目或历史回滚资产
- 可恢复网络请求采用同一操作 ID 的有界退避；超过预算转人工检查。图像生成非幂等，超时先查询提供者任务（若支持），不无条件重跑收费任务
- 替换/回滚未来扩展以新版本与原子指针更新实现，批准精确目标与新 manifest；不删旧图再重发

## 7. 图像校验细化

在模型编辑前后保留来源关系：source → theme-day → same-theme-night。普通到节日变体可以基于已批准普通白天图的编辑，但审核中须说明来源；节日夜景仍只能基于该节日白天图。

优先使用提供者真实透明输出；若不可用，适配器可选明确可分离的纯色背景并交由确定性抠图/去污染处理。不是所有提供者都需要旧项目的品红底，也不假设旧脚本许可可用。

校验分两层：自动层检查编码、alpha、边界/共享变换、可解码资源限制；视觉层检查招牌、主要门窗、结构和夜景一致性。指标用于发现问题，不保证语义真实性。最终 720/360/240 的所有展示与批准均来源于同一冻结字节版本。

## 8. 部署与安全

- 开发本地存储与演示 fixture 优先；生产之前建立独立 Worker、D1、R2、域名及单所有者认证。绑定名由实现确定，不能复用旧资源 ID
- 认证方案在第 0 阶段选定真实宿主支持的标准 OAuth/安全登录；勿自行拼出不完整 OAuth 协议。令牌最小权限、短期、可撤销；凭据创建/持久授权由用户批准
- 写接口严格认证、内容限额、速率限制和审计；浏览器 cookie 认证时有 CSRF 防护，CORS 最小来源，MCP audience 与目标环境一致
- 图像服务授权、部署权限和公开访问在真实需要时完成；本文件不包含 secrets 或可直接部署的账户配置
- Demo 默认 mock 模式、有可见标识、无生产写权限。确认包不能通过 query string 携带敏感数据

## 9. 待实施验证的决策

无需用户为每项技术细节提前作答：Kiro 可先用本地模拟完成核心链路，再根据实际环境选择传输、认证和依赖。对用户真正需要的输入只在相应阶段提出：外部图像服务授权/预算、持久凭据授权、部署目标与公开范围、可公开素材和赛事提交许可。入口登录只解决仓库访问，不等于这些后续授权。
