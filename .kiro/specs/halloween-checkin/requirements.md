# Requirements — Halloween Check-in

状态：实施前设计。`必须`为 MVP 验收门槛；`可选`不阻塞核心链路。所有测试待实现后实际运行。

## 用户故事与范围

我希望在熟悉的 AI 对话中发一张地点照片，说 `checkin` 或 `checkin Halloween`，得到认得出来的昼夜微缩建筑，先审核，再明确决定是否放到自己的展示网站。

不做城市组装、默认城市、位置推荐、多人社交、商家后台、公共注册平台或真 3D 重建。第一版是单所有者、多个兼容代理入口的系统。

## R1 输入与事实来源

- 当收到照片和 checkin 意图时，系统必须建立草稿，记录所选主题为 `normal` 或 `halloween`；没有节日指令时默认 `normal`
- 原图是该地点视觉事实的来源。若用户补充地点名字，仅当原图可见同一名字时才可作为招牌转录辅助；不得凭补充文字在图中添加原本不存在的招牌
- 地点、地址、GPS、原始拍摄时间和同行者均可空缺；不得从像素猜测精确地址/坐标。EXIF 存在也不自动公开，必须进入审核清单
- 无照片、照片不可访问、多个待选源图或关键意图冲突时，必须提出最小澄清。图库/网络图片不得悄悄替代用户原图
- 记录时间与照片拍摄时间分开，未知拍摄时间保持空。显示时区明确，不把服务器时间假装成拍摄时间

## R2 生成与主题

- 必须先生成白天版并检查身份，再仅用接受的白天图生成同一主题夜景。夜景只能改变照明，不应重画招牌、门窗、裁切、主结构或核心物件
- 默认保留来源的主要视角和建筑身份；若为微缩化做透视简化，必须在审核中说明，不引入新的主要建筑结构
- Halloween 模式必须保留地点可辨认度。新增装饰是明确的创意增添，不能把实际不存在的内容声称为现场事实
- 每个阶段最多两次生图：初次和一次明确核心错误修正。仍不合格则展示问题并等待用户选择，不能无限花费/重试
- 小字、非识别性细节或可由确定性后处理消除的背景问题，不应触发无休止重画
- 普通与节日成品必须各自独立存储；不能用节日图覆盖普通图。首次仅请求 Halloween 时可只生成节日一对，不强制额外生成普通一对
- 真实服务不可用时可以演示合成夹具，但必须标明模拟流程，不能假装生成成功

## R3 确定性图片准备与质量门槛

- 最终必须是 720×720 PNG、RGBA、有真实透明背景，而非绘制的棋盘格
- 一对图片必须使用共享缩放/平移参数；主体水平居中、底部对齐。建议初始取底边 y=651、主体最大边不超过画布 92%；这些为新实现待验证参数，不承诺与旧代码像素等价
- 必须检测文件真实格式、可解码性、尺寸、alpha、文件/解码资源限额和主题成对完整性。具体安全上限由实现中统一配置并覆盖边界测试
- 必须生成实际 360×360、240×240 预览并检查毛边、背景污染、招牌辨认度和过小/悬浮主体。几何一致性使用自动辅助指标加人审，不能仅靠文件尺寸判定
- 若透明结果无法在不删掉主体的前提下修好，必须失败；不通过放宽阈值掩盖问题。任意后处理改变成品字节必须使旧审核失效

## R4 审核、确认与发布

- 审核包必须包含来源预览（仅私密）、确切最终日夜图、小尺寸预览、主题、拟公开文案/元数据、未知项、差异和校验结果
- 用户在看到当前审核包后明确表达发布意图，才可发布该包一次。事前泛泛说“做一个”、同意改图或普通感谢不构成发布授权
- 审核包必须绑定不可变版本和 payload hash，覆盖目标项目、图片字节哈希及所有影响公开结果的元数据。任一字段或图片改变，旧批准立即失效
- 未批准、批准过期或已撤销时，必须拒绝启动新的发布操作；目标项目不符、哈希不匹配、校验未通过的请求不得启动发布或借重试绕过校验。已提交操作的查询与已有结果重放遵循 R5，不因批准随后过期/撤销而隐藏真实结果
- 服务端必须认证调用者并检查授权范围；不得信任代理提供的 owner ID 作为所有权证明。第一版可采用可信代理确认转述，但必须明确其信任边界，不将该转述视为服务端独立证明“人点击了同意”
- 发布前给出准确目标站点/可见性。生成完成、上传临时文件、显示预览都不能自动发布

## R5 幂等、失败与回滚

- 同一已批准版本、同一操作的重复请求必须返回已有状态或同一记录，不新增重复打卡；同一幂等键但不同 payload 必须报冲突。批准随后过期或撤销时，仍须在验证当前调用者身份、所有权、项目及原操作键/hash 绑定后，允许查询或幂等重放已有结果；不得创建新操作、写入新媒体/记录或重新触发发布等新副作用。尚未完成的操作仅报告实际状态；若恢复需要新的副作用，须重新审核和有效批准，不能把过期/撤销批准当成继续写入的授权
- 发布超时或返回不明时先查询操作状态与记录，再以同一键恢复；不得使用新键盲目重复发布
- 图片写入成功但数据库提交失败时，不出现可见的半条记录；未引用对象仅能由限定范围的清理流程回收
- 图片替换必须单独批准具体记录和新版本，保留旧版本以供回滚；回滚本身也需授权。MVP 可以先不提供替换 UI，但数据设计不能覆盖旧字节
- 永久删除不属于 MVP；实现时不得偷偷添加删除/清空生产资源的便利脚本

## R6 前端与可选氛围

- 网站必须显示已发布记录、主题与时间语义，提供日/夜查看，缺失一对的草稿不可作为完整记录展示
- 普通/节日生成版本的选择与日/夜选择必须独立；无该版本时清楚显示不可用，不暗中生成
- 可选网站 Halloween 氛围开关只改变展示，不调用付费/生图接口、不改变公开元数据、不替换记录图片。关闭后恢复普通呈现
- 必须支持移动端、键盘焦点、可辨识控件、图像替代文本与减少动态效果偏好

- **决定（2026-10-12，所有者）**：界面只提供两种模式。白天 = 普通版；夜晚 = 万圣节版（该地点没有万圣节版时显示其普通夜景），并带万圣节氛围。数据层仍分开保存主题和昼夜；模式切换只改变展示，不调用生成或发布接口。上面关于普通/节日与日/夜在界面上独立选择的条目，以这条决定为准

## R7 隐私、隔离与演示

- 必须使用独立开发/生产资源；本项目不触碰 August 生产资源。部署前必须检查目标账户、Worker、D1、R2、域名和连接器 audience
- 原图仅在请求所需的私密临时区域使用；完成/取消后按明确的保留策略清理，不写公开桶或 Git，不保存 EXIF 副本到公开资产
- 上传图片到第三方图像服务前，必须确保用户已授权具体数据与服务；更换服务不能沿用不适用的批准。凭据由安全流程配置，不由聊天收集
- 调试日志不得记录原图、令牌、完整敏感元数据；公开 API 不返回审核历史、内部存储键、源图或授权记录
- Demo 夹具只用合成素材或明确授权可公开素材；没有真实服务时页面明确提示 Demo。任何外部部署、公开仓库或赛事提交另行授权

## 验收场景

1. 普通链路：合成照片 → normal 一对 → 审核 → 确认 → 只出现一条记录，媒体可读且哈希一致
2. 节日链路：同一输入指定 Halloween → 节日一对 → 招牌/结构保留 → 批准后独立存储
3. 取消/修改：审核后改一个字符、主题、图片或目标环境 → 原批准不能发布
4. 重复与超时：双击、客户端重试、提交后断网 → 最终只有一个记录，状态可查询；提交后批准过期/撤销 → 正确所有者可查询或重放同一已有结果且零新副作用，新操作被拒绝；错所有者/项目或同键不同 hash 被拒绝，不泄露记录
5. 局部失败：第二张图片上传失败或 D1 提交失败 → 无半成品公开，后续恢复不重复
6. 恶意/异常输入：伪扩展名、损坏 PNG、超限图、错误尺寸、无 alpha、不同主体夜景 → 拒绝或要求修复
7. 权限：匿名写入、错项目令牌、其他所有者草稿、读取私密原图 → 拒绝
8. 显示：普通/节日 × 日/夜以及缺失节日资产均有明确行为；氛围开关请求日志中无生成/发布请求
9. 隐私：检查 Git、日志、公开列表及媒体响应，不含原图/EXIF/令牌/私密审批信息
